# ADR 0002：文章获取通道分层与降级顺序

## 状态

已接受（2026-08-21）。取代「`appmsgpublish` 是唯一列表来源」这一隐含架构假设。

## 背景

2026-07-30 起，公众号后台的 `/cgi-bin/appmsgpublish` 对本项目失效。这不是一次可等待的频控，而是**列表获取主路的消失**——项目此前所有的文章列表能力（`article discover`、`sync account`）都只走这一个端点。

2026-08-21 的实测证据：

| 端点 | 前提 | 结果 |
| --- | --- | --- |
| `/cgi-bin/searchbiz` | 后台会话 | `ret:0`，正常返回 fakeid/昵称/头像/简介 |
| `/cgi-bin/appmsgpublish` | 后台会话 | `200013`，查第三方号、查**自有号**均被拒 |
| `/mp/appmsgalbum?action=getalbum` | **无** | `ret:0`，单合集实测 1000 篇，`continue_flag=1` 可翻页 |
| `/s/{sn}` 文章正文页 | **无** | `200`，724 KB，`js_content`、标题、作者、`ct`、`biz` 完整 |
| `/mp/profile_ext?action=getmsg` | 个人微信凭据 | 无凭据时 `ret:-3, "no session"` |
| `/mp/getappmsgext` | 个人微信凭据 | 无凭据时 `ret:-2` |
| `/mp/homepage` | — | `ret:5` |

`appmsgpublish` 失效的排除性证据：同一会话的 `searchbiz` 正常（非会话失效）；查自有号同样被拒（非目标号问题）；当日新登录会话的**第一个**请求即被拒，且本地 job 历史显示 2026-07-28 之后再无一次成功（非短时频控）。

**未能区分**的是「端点全局下线」「本项目所用 mp 账号被封该功能」「出口 IP 被封」三者——区分需要第二个公众号账号或另一出口 IP。本 ADR 按最坏情况处理：**视为永久下线**。三种情况中有两种对普通用户是永久不可用，第三种对「任何用户都能用」这一目标同样不可接受，因此该区分不影响决策。

## 决策

### 决策一：三通道分层，按凭据成本降级

获取能力按**前提条件**而非按端点组织，调用方声明意图，由应用层选择通道：

- **通道 C（零凭据）**：文章正文页、`mmbiz` 资源、`/mp/appmsgalbum`。任何用户任何时候可用，无账号风险。
- **通道 A（后台会话）**：`/cgi-bin/searchbiz`。要求用户自有公众号并扫码登录。`appmsgpublish` 已从本通道移除。
- **通道 B（个人微信凭据）**：`/mp/profile_ext`、`/mp/getappmsgext`、`/mp/appmsg_comment`、付费内容。要求 `uin/key/pass_ticket/appmsg_token`，只能来自微信客户端流量。

降级顺序固定为 **C → A → B**：先用零凭据能拿到的，再用后台会话补账号元数据，最后才动用个人微信凭据。理由是风控主体不同——通道 B 的风险落在用户的**个人微信号**上，是三者中唯一不可承受的损失。

后台登录的定位随之改变：它从「核心能力」退化为**号码簿**，只负责 `searchbiz` 找号。不得再把后台会话作为任何列表能力的前提。

### 决策二：合集通道去除自我施加的会话门禁

`internal/wechat/album.go` 的 `ListAlbumArticles` 调用了 `discoverySession(ctx)`，但上游 `/mp/appmsgalbum` 实测**不要求任何 cookie**。该门禁是自我施加的，必须移除——它把当前唯一幸存的免凭据列表通道错误地绑定在了已经失去主要价值的后台会话上。

同时补齐合集通道的**扩散能力**：属于合集的文章，其公开页面内含所属 `album_id`（实测一篇文章同时暴露两个合集 ID）。因此建立「一篇文章 → 反查所属合集 → 枚举合集全部文章 → 每篇再反查其它合集」的递归发现路径，全程零凭据。

实现约束：合集接口返回的是 `http://` 链接且会 301，解析前必须跟随重定向。

落地时暴露出三个此前无人触发的缺陷，均已修复，记录在此以免重犯：

1. **公开文章页按 User-Agent 区别对待**。以本地客户端 UA 请求会收到 302 与约 1 KB 的空壳页，只有桌面浏览器 UA 才拿得到完整正文。`internal/download` 早已为此使用浏览器 UA，但 discovery 的文章页抓取没有，于是解析到空壳页并报成"文章结构异常"。该 UA 已上移为 `network.BrowserArticleUserAgent`，两处共用。
2. **合集条目的 `http://` 永久链接被 URL 校验拒绝**。校验要求 HTTPS，而上游合集**始终**返回 `http://`，因此每一个真实合集条目都会被判为非法 URL——`album traverse` 对真实上游从未成功过，而全部 fixture 都是 HTTPS，测试一直是绿的。现在接受 WeChat 白名单域名上的 `http://` 并**升级为 HTTPS** 后再使用，明文链接既不会被请求也不会被持久化。
3. **两条通道对 `aid` 的拼法不一致**。文章列表用 `{appmsgid}_{itemidx}`，合集用 `{msgid}:{itemidx}`，而 `identity.ArticleID` 直接对 `aid` 取哈希，导致同一篇文章按来源不同落成两行。合集侧已改用同一拼法，并有测试直接断言两条通道产出同一个 ID。

第三点尤其值得警惕：本 ADR 决策三把"`aid` 可跨通道重建、多通道结果天然去重"当作前提，而该前提在合集通道上原本是不成立的。任何新增通道都必须以测试证明它与既有通道的文章身份一致，不能假设。

局限必须在用户可见处说明：合集只覆盖作者主动归类的文章，未使用合集功能的公众号（实测宝玉AI）在本通道下拿不到任何列表。

### 决策三：`profile_ext` 作为列表主路，但其可用性是**未验证假设**

`appmsgpublish` 下线后，能拿到「全量、按时间序」文章列表的只剩 `/mp/profile_ext?action=getmsg`。因此 `--via credential` 不是降级选项，而是默认主路。

但当前**只证明了该端点仍在响应**（无凭据返回 `no session`），**未证明带上有效凭据它仍返回文章列表**。在该假设被实测证伪或证实之前，不得围绕它构建大规模实现。验证顺序：先取得一份真实凭据打通一次调用，再写解析与同步通道。

数据契约上已确认可行的部分：文章身份 `identity.ArticleID(fakeID, aid)` 中的 `aid` 形如 `{appmsgid}_{itemidx}`，而 `profile_ext` 的 `content_url` 带 `mid`/`idx`，可重建出同一 `aid`。**两条通道拿到的同一篇文章会命中同一行，不会产生重复**，这是多通道并存的前提。

已知契约缺口：`profile_ext` 不返回 `total_count`，只有 `next_offset`/`can_msg_continue`；而 `internal/library/articles.go` 无条件写入 `UpstreamTotal`，会把已知总数覆盖为 0。接入前必须把 `UpstreamTotal` 改为可选语义，并将完成判定从 `next >= total` 改为认 `can_msg_continue`。

### 决策四：凭据获取以被动捕获为默认，主动翻页为例外

凭据只能来自微信客户端流量，浏览器无法产生（微信 App 会话不与系统浏览器共享）。本地 MITM 捕获是唯一的自动化获取方式，其边界：

- 只对 `mp.weixin.qq.com` 解密，其余 CONNECT 一律盲转发，不解密不落盘；
- 只监听回环地址；机器已有系统代理时必须链式转发至原上游，不得使其它流量失去路由；
- 自签 CA 私钥进 keyring 或显式加密 vault，证书短期有效，提供一键吊销与卸载；
- 捕获物只保留 `uin/key/pass_ticket/wap_sid2/appmsg_token/biz`，其余请求与响应内容不得持久化；日志只输出字段名与非敏感元数据，不输出值。

**被动优先**：MITM 常驻期间不主动构造请求，只从用户正常浏览产生的流量中收集凭据与文章 URL。此模式不产生任何额外上游请求，风控风险为零。主动翻页（例如用凭据连续拉取 85 页）属于例外路径，必须复用同步作业的 `page-delay` 与 checkpoint，不得挂在无节流的 `discover --all` 上。

### 决策五：明确不做

- **不枚举 `sn`**：文章链接中的 `sn` 是随机 token，不可穷举，任何尝试都是无效流量。
- **不试图从浏览器取个人微信凭据**：实测 `no session`，原理上不成立，不再重复验证。
- **不引入第三方索引/镜像站**作为发现来源：来源不可靠、反爬对抗无止境，且会把项目拖入与本地归档目标无关的维护负担。
- **不把后台会话重新变成列表能力的前提**。

## 后果

### 正面

- 项目主体能力（正文、资源、解析、导出、本地库、对象存储、作业引擎、备份恢复）完全不受 `appmsgpublish` 下线影响，无需改动。
- 合集通道解锁后，对使用合集的公众号可在**零凭据、零登录**下取得千篇量级的列表，是当前性价比最高的发现路径。
- 通道分层后，「能拿到什么」由用户已具备的前提决定，而不是由某一个上游端点的存亡决定；再有端点失效时，影响面被限制在单一通道内。
- `aid` 可跨通道重建，多通道结果天然去重，允许混合使用而不污染本地库。

### 负面 / 持续义务

- **列表能力整体降级**：未使用合集的公众号，在没有个人微信凭据时无法取得任何文章列表。这是上游造成的能力损失，不能靠实现弥补，必须如实告知用户。
- **通道 B 把风险从公众号转移到个人微信号**。任何主动请求路径都必须节流、可中断、可续跑，并在文档中明示风险主体的变化。
- **MITM 引入本地监听面与用户信任库变更**，需要长期维护 CA 生命周期、卸载路径与跨平台差异；macOS 之外的客户端支持未做评估。
- **`profile_ext` 可用性未验证**，且即使当前可用，它与 `appmsgpublish` 同属可被上游随时关闭的接口。项目不应假设任何单一上游端点长期存在——本 ADR 的分层结构正是为下一次失效准备的。
- 凭据 `key` 有效期约二三十分钟，需要过期预警、作业自动暂停与恢复；`pause jobs on throttling`（commit `81bebb1`）提供了骨架，但尚未覆盖凭据过期语义。
- 需补充 `UpstreamTotal` 可选语义与 `can_msg_continue` 完成判定的迁移与测试，否则接入通道 B 会破坏已有账号的总数统计。
